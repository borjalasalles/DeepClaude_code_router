# Session 2026-05-14 — M1 pre-flight: riesgos y secuencia

## Context

Revisión del estado del proyecto antes de iniciar la implementación de M1. Objetivo: validar si los próximos pasos tienen sentido desde una perspectiva de sistemas agénticos y DevOps, e identificar riesgos antes de escribir código.

## Decisiones y hallazgos

### 1. Diseño v0.2 validado — sin deuda arquitectónica pendiente

El diseño está bien fundamentado. Las tres decisiones clave son correctas:
- Whitelist semántica para el clasificador de publicidad (conservadurismo en el lugar correcto).
- Regla dos-de-dos (PII scan limpio AND publicness classifier aprueba) como única forma defensivamente correcta.
- No LLM-as-judge para guardrails de privacidad (Cap 3 p.144 + Cap 10 p.457).

### 2. Gateway: thin custom, no Portkey ni MLflow

**Decisión:** el gateway será tres clientes LangChain configurados desde `.env`, uno por tier.

Portkey añade coste fijo y un punto de fallo externo. MLflow AI Gateway es demasiado pesado para este escenario. El requisito de M1 — per-tier upstream selection — se resuelve con tres instancias `ChatOpenAI`/`ChatAnthropic` con `base_url` distinto. No se necesita un gateway externo.

El open question de `design.md §10` queda cerrado: **thin custom**.

### 3. Punto de integración con deepagents — RESUELTO vía `class_path`

**Investigación de documentación oficial completada en sesión 2026-05-14.**

deepagents soporta tres mecanismos de configuración de modelo en `~/.deepagents/config.toml`:
- `base_url` — endpoint OpenAI-compatible custom (Opción B: sidecar local)
- `api_key_env` — env var con credencial
- `class_path` — subclase `BaseChatModel` totalmente custom instanciada por el CLI (Opción C)

**Decisión: Opción C (`class_path`).** Es el mecanismo oficial de extensión. El CLI instancia `RouterChatModel` directamente en el mismo proceso — sin red intermedia, sin proceso externo, sin fork del upstream.

```toml
# ~/.deepagents/config.toml
[models.providers.deep-devops]
models     = ["router"]
class_path = "deep_devops.router.model:RouterChatModel"
enabled    = true
```

```python
# deep_devops/router/model.py
class RouterChatModel(BaseChatModel):
    def _generate(self, messages, stop=None, run_manager=None, **kwargs):
        # 1. PII scan  →  2. publicness classifier  →  3. tier dispatch
        # 4. Log JSONL (ttft, cost, tier, route_decision)
        ...
```

```bash
deepagents --model deep-devops:router
```

**Por qué mejor que sidecar (Opción B):** no hay salto de red, no hay proceso extra que gestionar, el router tiene acceso directo al contexto Python de la sesión, y es testeable unitariamente sin levantar un servidor.

**Fuente oficial:** `docs.langchain.com/oss/python/deepagents/cli/configuration` — campo `class_path` en `[models.providers.<name>]`.

### 4. PII scanner necesita fixtures antes del primer regex

El scanner es un guardrail de seguridad con error one-way (un falso positivo = fuga de datos interna a China). Sin un eval set mínimo de ~50 casos desde el día 1, no hay forma de saber si los patrones regex cubren todos los formatos reales.

**Acción:** crear `evals/pii_scanner/` con casos positivos (PII real), negativos (texto limpio) y adversariales (near-miss) antes de escribir el primer regex.

### 5. Nebius es bloqueador externo para el gate completo de M1

La cuenta de Nebius depende del CTO. Mitigación: usar DeepSeek native como stub de tier-2 durante el desarrollo (misma API OpenAI-compatible, distinto endpoint). El gate de M1 se verifica con Anthropic + DeepSeek native; Nebius se incorpora cuando llegue la cuenta (redefinir como parte de M1 o inicio de M2).

### 6. Chat templates y portabilidad de system prompt entre tiers (Cap 5 p.216-217)

El riesgo de "chat template equivocado" de Cap 5 **no nos afecta directamente**: los tres tiers usan chat/messages APIs (no completion con texto crudo). LangChain envía JSON estructurado (`role/content`) y el servidor aplica el template internamente.

El riesgo real en nuestro caso es distinto: **portabilidad del system prompt en escalación**. Cuando escalamos de tier 1/2 (DeepSeek) a tier 3 (Claude), enviamos el mismo system prompt —calibrado por deepagents para el modelo registrado— a un modelo diferente. Claude responderá algo razonable (silent failure, p.217) aunque el prompt no esté optimizado.

**Decisión: no catálogo de prompts en el MVP.** La solución correcta es `TIER_SYSTEM_SUFFIX` dentro de `RouterChatModel._generate()`: un sufijo mínimo por tier, versionado en git, testeable. Para tier 3 (Anthropic), se añade un sufijo de contexto mínimo en M2 cuando haya datos de escalación reales. Un catálogo YAML especulativo viola la regla "no skills especulativos".

deepagents ofrece `HarnessProfile` para esto pero opera a nivel del modelo que deepagents ve (nuestro RouterChatModel). Como RouterChatModel despacha internamente, el control de system prompt por tier vive dentro de `_generate()`.

Roadmap del prompt catalogue:
- M1: nada — LangChain resuelve template, system prompt genérico funciona en los tres
- M2: `TIER_SYSTEM_SUFFIX` para tier 3 en RouterChatModel
- M3: tabla `(task × tier)` con datos reales de Cap 4 Table 4-3; catálogo si los datos lo justifican

## Rationale

- La integración via `class_path` sigue Cap 10 p.473: no añadimos orquestación sobre deepagents ni modificamos el upstream.
- Fixtures antes de código sigue Cap 4 §Design Your Evaluation Pipeline — criterios de aceptación antes de implementación.
- Aplazar publicness classifier a M2: es la pieza más sutil (whitelist + file-path allowlist + marker negatives), merece iteración propia.
- No prompt catalogue especulativo: misma regla que "no skills especulativos" — Cap 3 p.146 + regla del proyecto.

### 7. Bug detectado: config.toml `recent` sobrescrito por el TUI

El TUI de deepagents sobreescribió `recent = "openai:deepseek-chat"` al cambiar de modelo desde la UI. Esto rompe los intentos de resumir sesiones con `-r` porque la sesión guardada queda ligada al provider incorrecto.

**Síntoma:** `Error: Agent error: {'error': 'NotFoundError', 'message': 'An internal error occurred'}` al intentar `deepagents -r <thread-id>`.

**Fix aplicado:**
```toml
# ~/.deepagents/config.toml
[models]
default = "deepseek:deepseek-chat"
recent  = "deepseek:deepseek-chat"
```

**Regla:** nunca cambiar el modelo desde el TUI — usa siempre `--model deepseek:deepseek-chat` en el flag de lanzamiento. En el futuro será `--model deep-devops:router`.
